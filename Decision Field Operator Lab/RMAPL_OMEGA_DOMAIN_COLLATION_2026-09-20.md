RMAPL/Ω is derived **upward from native executed/declared contracts** and then audited **downward by reconstruction**.

```text
NATIVE DATA
-> NATIVE CONTRACT
-> NATIVE VERIFIER / COUNTERPROBE
-> INSPECTABLE RESULT
-> CANDIDATE SHARED ROLE
-> Ω PROJECTION
-> NATIVE RECONSTRUCTION OR EXPLICIT LOSS/REMAINDER
```

No abstraction is promoted because the same word appears in several projects.

```text
COMMON != COMPLETE
CONNECTED != MERGED
METHOD_TRANSFER != EVIDENCE_TRANSFER
DOMAIN_REMAINDER != DEFECT
DESIGN != ACTIVE_RUNTIME
```

## 14. Promotion rule

A generic RMAPL/Ω role is promoted only when it has:

1. a concrete native fixture;
2. a consequential purpose;
3. explicit native remainder;
4. round-trip or loss accounting;
5. no authority/evidence promotion;
6. a counterexample or refusal case;
7. a versioned validation record.

Cross-domain recurrence strengthens the case; it does not establish universality.

## 15. Current conclusion

The repository supports a shared repair/fitting calculus, but only as a domain-derived, evidence-bounded projection.

RMAPL is the proposed executable authoring surface for conditional repair/fitting.

Ω is the minimal common interchange/inspection envelope.

Decision Field remains the task-local decision/control structure.

RMAL remains the currently implemented cooperation/provenance carrier and toolchain surface unless a future explicit compiler integration promotes RMAPL constructs into RMAL.

RMALKDVMLLL remains a broader VM/link-layer line and is not redefined by this design.
